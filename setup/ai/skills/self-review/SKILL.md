# 過去指摘の水平展開チェック

対象ブランチの **コミット済み差分** が、過去に指摘されたパターンを再発していないかを確認する。
設計・品質・テスト十分性の網羅レビューはしない。

## 前提

| 項目 | 必須 | 用途 |
| ---- | ---- | ---- |
| 対象リポジトリ | ✅ | ローカル diff |
| 指摘ディレクトリ | ✅ | 対象 md を必ず Read する。解決方法は下記 |

**指摘ディレクトリ（スキル本体ではない）:**

両方を読む。リポジトリ名のディレクトリは作らない。

| 種類 | パス | 置くもの |
| ---- | ---- | -------- |
| 共通 | `~/.cursor/skills/self-review/findings/` | リポジトリを問わない指摘 |
| 固有 | `<repo>/.cursor/self-review/findings/` | そのリポジトリだけの指摘 |

ホーム配下にリポジトリ固有の指摘は置かない。

対象は各ディレクトリ直下の `*.md`。ファイル名は問わない。ベース名が `ignore_` で始まるファイルは読まない。再帰しない。`SKILL.md` は対象外。

ファイルは最初は 1 つでよい。膨大になったら **観点ごと** に分割する。1指摘1ファイルにはしない。

- 分割前、および同じ観点の追記は既存ファイルへ書く
- ファイルが大きくなった観点、または新しい観点はファイルを増やす
- 一時的に外すだけなら、そのファイル名に `ignore_` を付ける

指摘の追加・修正は指摘ディレクトリ内だけを編集する。SKILL.md に個別指摘を書かない。

## 対象外

- チケット要求との網羅的な整合（Design 全般）
- セキュリティ・性能の新規探索
- 今回触っていない既存コードの過去違反を NG にすること（参考言及は可）

## 実行フロー

```text
進捗:
- [ ] Phase 0: 対象ブランチと diff の確定
- [ ] Phase 1: 指摘ファイルを読む
- [ ] Phase 2: 適用対象の選定
- [ ] Phase 3: 項目ごとの確認
- [ ] Phase 4: 結果を返す
```

### Phase 0 — 対象

1. ブランチ未指定なら現在ブランチ。`<base>` は明示があればそれを使う。なければ `origin/HEAD` のデフォルトブランチ。
2. `origin/<base>` を最新化してから `origin/<base>...<target_ref>` の diff を取る。`<target_ref>` は現在ブランチの HEAD。
3. 未コミット変更は対象外。あれば一言だけ知らせて続行する。
4. 変更ファイル一覧を取る。巨大 diff でも全ファイルを対象にするが、指摘と無関係な生成物（生成コードや lockfile の機械的差分など）は適用判定をスキップしてよい。

### Phase 1 — 指摘ファイル

1. 共通・固有の両方について、対象 `*.md` をすべて **全文 Read** する。
2. 片方だけ無いのは続行する。どちらにも対象が無い場合はチェックを打ち切らず、パスを示してユーザーに確認する。

### Phase 2 — 適用対象

各指摘の **適用条件** と今回の差分を照合する。

- 条件に当たらない → `N/A`（確認しない）
- 当たる → Phase 3 で確認する
- 「採用しなかった」と書いてある項目は、**同じ対象への再指摘はしない**。新規の同型コードが別判断なら ASK

適用は差分の新規・変更コードが主。類似の既存実装を見るのは、差分が触ったファイルと、そこに並ぶ同型（同じテストファイル内の隣接ケースなど）に限る。リポジトリ全体の探索はしない。

### Phase 3 — 確認

適用する各指摘について:

1. 指摘の「確認すること」を、今回の差分に当てる。
2. 根拠はファイル:行（または PR 本文・コミットメッセージ）で示す。
3. 判定は次のいずれか 1 つ。

| 判定 | 意味 |
| ---- | ---- |
| OK | 水平展開できている。または意図的除外が差分・コメントに残っている |
| NG | 過去指摘と同じ穴を、今回の新規/変更コードが踏んでいる |
| ASK | 適用はされるが、意図が差分から読み取れない |
| N/A | 今回の差分に適用条件が無い |

NG は「直すべき」事実だけを書く。大規模リファクタやチケット外の既存コード修正は提案しない。

### Phase 4 — 結果

チャットに以下だけ出す。レポートファイルは作らない（ユーザーが保存を頼んだときだけ）。

```markdown
# 水平展開チェック

- **ブランチ**: `<branch>`
- **対象**: `origin/<base>...<target_ref>`
- **指摘**: （使ったディレクトリと読んだファイル）

## 要約
NG: N ｜ ASK: N ｜ OK: N ｜ N/A: N

## 要対応
### 指摘の見出し — NG または ASK
- **対象**: `path:line`
- **ギャップ**: （過去指摘に対して今回足りないこと。1〜3文）
- **推奨**: （今回の差分の範囲でやること）

## 適用結果
| 指摘 | 判定 | 一言 |
| ---- | ---- | ---- |
| 見出し | OK / NG / ASK / N/A | ... |
```

- 見出しは指摘ファイルのものをそのまま使う。スキル側で ID を付けない。
- 要対応は NG → ASK の順。OK / N/A の詳細は表の一言で足りる。
- 過去ファイルに無い新規指摘は出さない。見つけても水平展開の結果には混ぜない。必要なら「指摘ファイル外の気付き」を最大 3 件、末尾に分ける。
- 指摘ファイルへの追記が有用なら、追記案を 1 件まで提案する。ユーザーが同意するまでファイルは更新しない。

## 指摘ファイルの更新（依頼されたときのみ）

ユーザーが「指摘を足して」と言ったとき:

1. リポジトリを問わない指摘は共通ディレクトリへ、そのリポジトリだけの指摘は固有ディレクトリへ書く。既存ファイルへ追記する。膨大になった観点、または新しい観点だけ新規ファイルにする。1指摘1ファイルは作らない。
2. 個別 PR の再録ではなく、**次のブランチで機械的に確認できるパターン**にする（適用条件 + 確認すること）。
3. 共通ファイルには、プロジェクト固有の名前、PR / チケットの URL や ID を書かない。コード例は型名・関数名・変数名を汎用にする。出典が必要なら固有ファイルへ書く。
4. 採用しなかった指摘は「採用しなかった」と理由を残し、再指摘しない旨を書く。
5. 一時的に外すだけなら、削除せずその観点ファイル名に `ignore_` を付ける。
